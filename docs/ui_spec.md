# 3ペインUI仕様

プロフィールのフォロー承認待ち表示にはフォロー解除ボタンを併設し、承認前のリクエストを取り消せる。NoteCardのフォロー状態スイッチも承認待ち状態で操作すると同じ解除APIを呼び、未フォロー状態へ戻す（#204）。

## 「開く」ダイアログ（#165）

左メニューの「🔗 開く」は「🔍 検索」と同列・直後に配置し、URL・AT URI・`@`で始まるユーザーID・`did:plc:` DIDを入力するモーダルを開く。「開く」で必要に応じて対象を取り込み、プロフィールまたはポスト詳細へ遷移する。判別不能な入力はモーダル内に表示する。

案内文は通常時に「URLまたはユーザーID」、画像認識時に「QRコードまたは文字をかざしてください」と表示する。入力欄右端のカメラアイコンボタンで画像認識を開始し、背面カメラを優先して各フレームをQRデコーダー、2秒ごとにOCRへ渡す。条件に合う文字列を認識したら入力欄へ戻る。モーダル終了時はMediaStreamとOCR Workerを停止する。

対象読者: フロントエンド（`frontend/`, React + Vite + TypeScript）に触れる開発者。画面レイアウトとUX導線のみを扱う。コンポーネント構成は `docs/architecture.md` 8節参照。

投稿カードと他ユーザーのプロフィールの「⋯」メニューには「⚠️ 通報」を表示する。通報モーダルは
Bluesky準拠理由を必須とし、自由記述は300文字/1000バイト以内、通報先はローカル対象なら自サーバー
固定、Fedi/Bsky対象なら自サーバーまたはリモートを選べる。管理画面の「通報」タブは未処理を先頭に、
対象リンク、クローズ、凍結/投稿削除、内部コメント、リモート転送を提供する。
管理者が通報対象リンクから投稿詳細またはユーザープロフィールを開く場合は、
followers-only/directを含む非公開投稿も閲覧できる。

## 1. 3ペイン共通レイアウト・グリッド構造

デスクトップおよびタブレット環境において、画面の横幅（デッドスペース）を情報の深掘りにフル活用するためのグリッドシステム。

* **左ペイン（幅固定：小 / `flex-basis: 240px`）:** メインメニュー（ホーム、通知、検索、プロキシ設定、投稿ボタンなど）。
* **中央ペイン（幅固定：中 / `flex-basis: 600px`）:** メインのコンテンツストリーム。
* **右ペイン（幅固定：中〜大 / `flex-basis: 500px`）:** ダイナミック・コンテキスト領域（画面のルートに応じて裏でシームレスに変形する）。

### 1.1 モバイルレイアウト（幅768px以下）
* 左ペインは非表示になり、代わりに画面下部へ5つのフローティングボタンを左から順に配置する。
  * **左下:** メインメニューを開くボタン（ドロワー表示、DM未読バッジ付き）。
  * **左から2番目（#180）:** `/`（ホーム画面）へ遷移するボタン。
  * **左から3番目（#75）:** `/notifications`（通知画面）へ遷移するボタン。
  * **右から2番目:** `/search`（検索画面）へ遷移するボタン。
  * **右下:** 新規投稿モーダルを開くボタン。
* 中央ペイン・右ペインは縦積みの1カラムになる。
* `body`単独（`frontend/src/index.css`）に`overflow-x: hidden`を設定し、子孫（NoteCard等）が万一横方向にはみ出してもページ全体の実効幅（モバイルブラウザのレイアウトビューポート）が広がらないようにする。モバイルでは中央ペインが画面幅いっぱいのため、これによりフローティングボタン列（`position: fixed`、`left`/`right`指定）の位置基準は常に中央ペインの実寸と一致する（はみ出しに引きずられてボタン位置が画面外へ流れる事故の防止、#長いニックネームはみ出し対策）。`html`側は触らずvisibleのままにすること（CSS仕様の「body→viewport」伝播ルールが効き、bodyが独自スクロールコンテナ化しない）。`html, body`両方や`.shell`等ネストした`div`に付けると、`overflow-x`/`overflow-y`連動の仕様によりそのdiv/bodyが独自の縦スクロールコンテナ化し`window.scrollY`ベースのスクロール位置復元が壊れる（実機確認済みの回帰）。

### 1.2 NoteCardヘッダー（投稿者名・日付・アカウント行）

* 1行目: 表示名（あふれる分は`hidden`+ellipsis）と、右寄せの投稿日付。日付は常に全文表示を優先し、表示名側だけを縮める。
* 2行目: アカウントID（`@user@domain`、配送先/公開範囲の小バッジ込み、あふれる分は`hidden`+ellipsis）と、その右に続く「リモートサーバー表示」。
  * ローカル投稿者・seiran間連合（`remote_seiran`）では表示しない（`remote_seiran`は従来通りアカウントID直後の小バッジ🀄のみ）。
  * Fedi/Bskyのリモート投稿者にのみ表示する。Fediはサーバーアイコン（`note.user.instance.iconUrl`、バックエンドが`<link rel="icon">`/`/favicon.ico`から解決・未取得時は🌐絵文字にフォールバック）＋サーバー名称（`note.user.instance.name`、nodeinfo未取得時はドメイン名で暫定表示）、Bskyは投稿フォームと同じBlueskyロゴSVG＋「Bluesky」固定表示。
  * ローカル投稿の配送先バッジ（アカウントID直後の小バッジ）も、Bsky配送分は🦋絵文字ではなく同じBlueskyロゴSVGを使う。
  * 背景色はバックエンドが解決済みの最終値（`note.user.instance.themeColor`）をそのまま使う。フロントエンド側にsoftware別の色分けロジックは持たない（`docs/database.md`の`remote_instance_meta`参照）。リモートが宣言する`themeColor`は暗色もありうるため、文字色は常時濃色固定（サイトのダーク/ライトテーマに関わらず読める必要があるため）に加えて白いドロップシャドウで縁取り、暗い背景色でも文字が沈まないようにする。
  * アカウントID表示の右からNoteCard右端まで幅いっぱいに広がり（`flex: 1 1 0`）、あふれる分は表示名と同様`hidden`+ellipsisで切る。
* リポストラッパーの場合、rail（🔁 + リポストした人 + 日時）とその下の元投稿カード（`Note.renote`）は別々の詳細画面を指すため、それぞれの日付は常にそれぞれの詳細画面（rail: リポストラッパー自身`/notes/:id`、元投稿カード: 元投稿`/notes/:renoteId`）へのリンクとして機能する。親から`linkToDetail={false}`（自ページ自身への自己参照リンクを消すためのフラグ、ポスト詳細画面の主役カード表示で使用）が渡されても、元投稿カード側には伝播させない（別ページである以上リンクは常に有効）。

## 2. 各画面における右ペインの動的コンテキスト・スイッチ

ユーザーが現在見ている中央ペインのコンテキスト（画面状態）をフロントエンドの状態マネージャーが監視し、右ペインの内容を最適化する。

### 2.1 【タイムライン画面】表示時

* フィードごとの可視性は、ホーム/ソーシャルでは自分またはフォロー中の「ひかえめ」「プライベート」投稿を表示し、ローカル/グローバルでは投稿者本人が閲覧している場合も両方を表示しない。フロントエンドでもローカル/グローバルの取得結果を同じ条件で最終フィルタする（#105）。
* **右ペインの構造:** タブ切り替え式。デフォルトタブは【クイック通知】（トレンド集計はバックエンド未実装のプレースホルダのため、機能している通知を優先表示する方針）。
  * **タブ1: 【クイック通知】（デフォルト）** 自分へのリプライやリアクションの簡易ストリーム。中央のメインTLを消費しながら、自分への反応を右目でリアルタイムに監視できる。DB永続化済みで新着順の無限スクロールに対応（`docs/protocols.md` 8節）。通知者のユーザー名は種別によらず常にプロフィールページへのリンク。リプライ・リアクション・メンション通知は対象ポストが特定できるため、通知文全体（アイコン以外）がそのポストへのリンクになり、通知アイテムへのマウスオーバーでは対象ポストの投稿者と本文をポップアップ表示する。ポップアップは返信先表示と共通の `NoteHoverPreview` を使い、初回ホバー時のみ取得・120ms遅延クローズとする（フォロー系通知は対象ポストが無いためリンク・ポップアップなし）。対象ポストがCW付きの場合、`NoteHoverPreview`もCW案内文と開閉ボタンのみを初期表示し、本文はボタン操作後にのみ表示する（`NoteCard`本体のCW挙動と同じ）。
  * **タブ2: 【トレンド＆検索】** 検索窓 ＋ 現在の二大宇宙（AP/ATP双方）の集計から算出されたリアルタイムトレンドワードランキング（トレンド集計は未実装、検索のみ機能）。

#### 投稿フォームのリッチ入力（#94）

入力面の `ComposerEditor`（contenteditable）は、iOS Safariがフォーカス時にページを自動拡大しないよう、ルート文字サイズに依存せず16pxを維持する（#208）。この方針はアプリ全体のフォーム要素（`input`/`textarea`/`select`）に共通する: いずれもフォーカス対象のcomputed font-sizeが16px未満だとiOS Safariが自動ズームするため、rem指定やUA既定値に任せず、各要素自身に`font-size: 16px`をpx単位で明示する。
* 投稿本文は送信時には従来どおりプレーンテキストへ直列化するが、入力面は `ComposerEditor`（contenteditable）で装飾表示する。
* 半角 `@` または絵文字の開き `:` からカーソル位置までのトークンに対し、投稿欄専用のアクター前方一致APIまたは公開カスタム絵文字一覧を使った候補を入力欄の下へ表示する。アクター検索は先頭`@`を除いた入力でハンドルだけを前方一致させ、表示名・ハンドル途中の部分一致は対象にしない。完成済み絵文字の閉じ `:` は候補を発火しない。上下キー・Tab・Shift+Tabで候補を選び、候補選択中のEnterのみ置換に使う。候補未選択時のEnterは1回につき改行を1個挿入する。IME変換中は候補キー操作を横取りせず、未確定DOMを装飾・再構築せず、変換確定後にプレーンテキスト値へ同期する。未確定文字はcontenteditable自身のDOMに置かれるため、入力開始時点でプレースホルダーを隠す。逐次入力中に非同期のID既知判定で装飾DOMを更新する場合もcaretを保存・復元し、完全修飾Fedi/Bsky IDまで入力と候補表示を継続できるようにする。
* ローカルユーザーの候補表記は入力に合わせる。`username`への前方一致なら`@username`、`username@`への前方一致なら`@username@local.domain`、それ以外のローカルBskyハンドル一致なら`@lower(username).local.domain`を返す（Bskyハンドルは小文字のみ）。完成したメンションはactorsテーブル上で完全一致した場合に水色背景・青太字、未解決の場合にピンク背景・赤太字で表示し、ローカルユーザーはこの3形式を既知として扱う。
* 完成したローカルカスタム絵文字shortcodeは、NoteCardと同じく閉じコロンの直後が文末または英数字・`_`以外の場合に限り、縦1.5em・アスペクト比維持の不可分な画像として表示する。左右キーでは絵文字内部へ入らず前後へ移動し、直前または直後でBackspaceを押すと隣接するコロンだけを削除して通常テキストへ戻す。

### 2.2 【ユーザー詳細画面】表示時（左右並列プロフィールレイアウト）
Misskey等に代表される「自己紹介やメタデータが縦に非常に長いプロフィール」を開いた際、スクロール地獄を完全に破壊するための特権レイアウト。
* **この画面（`/:acct`、`/@handle`形式）と旧`/profile?q=`はログイン不要で閲覧できる。** `App.tsx`のルーティングで`RequireAuth`によるガードを外している。プロフィール取得・投稿一覧・フォロー中/フォロワー一覧の各APIは元々`MaybeAuthedUser`/任意認証で未ログイン対応済み。未ログイン時は対ユーザー操作メニュー（下記）の代わりに「フォローするにはログインするか、ユーザーIDをいつものサーバーで開いてください」というガイダンス文を表示し、フォロー・ミュート・ブロック・通報の操作自体を露出しない。
* **中央ペイン:** ユーザーのヘッダー、アイコン、Bio、フォロー数・フォロワー数（クリックで右ペインの対応タブへ切り替え）、各種プロトコルアイデンティティ（DID/URI）、および「ピン留めされたポスト」を固定描画。Bio中の`:shortcode:`はノート本文・表示名と同様にカスタム絵文字画像へ展開する（ローカルアクターは`custom_emojis`照合、リモートFediアクターはAP `tag`由来の`emoji_map`を使用。Bskyアクターは展開しない）。
* **アカウントID表示:** ローカルユーザーは他サーバーが存在しないためサーバー名表示エリアを持たず、代わりにFedi形式（Fediverseロゴアイコン、`@username@domain`）・Bsky形式（Blueskyロゴアイコン、`@username.domain`）の両IDを2行で書き並べる。リモートユーザー（fedi/bsky）はIDを1行（`@username`または`@username@domain`）のまま先頭にプロトコルアイコン（Fediverseロゴまたは Blueskyロゴ）を付け、その直下にNoteCardと共通の「サーバー名表示エリア」（`lib/format.ts`の`remoteServerBadgeInfo`、サーバーアイコン・フレンドリーネーム・テーマカラー背景。Bskyは固定表示、Fediはバックエンドが解決したインスタンス情報`ProfileResponse.instance`を使用）を表示する（#NoteCardリモートサーバー表示、旧🌐Fediverse/🦋Blueskyバッジを置き換え）。管理者に凍結されているローカルユーザーの場合のみ、Fedi形式ID行の直後に【凍結中】インジケーターを表示する（`ProfileResponse.is_suspended`、リモートアクターは常に`false`）。
* **右ペイン:** **タブ切り替え式（【アクティビティ】【フォロー中】【フォロワー】）。** デフォルトタブは【アクティビティ】で、そのユーザーの投稿イベント＋絵文字リアクションイベントを時系列混合で全面描画する（`ProfileFeedList`、`GET /api/users/posts?includeReactions=true`）。投稿は通常の`NoteCard`（リポストは閲覧可能な元投稿をカード内へ埋め込んで表示）。リアクションイベントはクイック通知タブ（`NotificationsPanel`）と同じ体裁のカード（`ReactionEventCard`）で、「[リアクション画像] [対象ポストの投稿者]のポストにリアクションしました」の1行を表示し、クリックで対象ポストの詳細画面へ遷移する（このタブは表示対象＝リアクションした人がプロフィール本人に確定しているため、通知パネルと違い「誰が」は文面に含めない）。初回取得・無限スクロール追加取得とも同一APIで、カーソルは投稿・リアクション共通の`until_id`（`posts.id`/`reactions.id`はいずれも`generate_snowflake_id`採番で同一名前空間、`docs/database.md`参照）。【フォロー中】【フォロワー】タブはそれぞれのアクター一覧（アイコン・表示名・acct、クリックで相手のプロフィールへ遷移）を無限スクロールで表示する。DB未登録のリモートアクター（AppView直取得で未フォローのBskyユーザー等、`actor_id` を持たない）はフォロー一覧を取得できないため、この場合はタブなしで従来通り投稿一覧のみ表示する。
* **スクロール挙動:** 中央ペインと右ペインのスクロール機構を完全に独立（`overflow-y: auto`）させる。右ペインをどれだけ過去にスクロールしても、中央のプロフィール（対ユーザー操作メニュー等）は画面に固定され続ける。
* **狭幅（`useIsNarrowViewport`、1400px以下。右ペインが中央ペインの下に落ちる幅）では、ピン留めポストを独立セクションとして表示せず、【アクティビティ】【フォロー中】【フォロワー】タブシートの先頭タブ【ピン留め】として統合する（ピン留めが無ければ従来通り【アクティビティ】が先頭タブ）。** このタブシートは中央ペイン上部の見出し（`panel.header`）の直下にsticky固定される（見出しの実高さを`ResizeObserver`で計測し`top`オフセットへ反映、2.4dのフィードタブと同じ手法）。広幅では従来通り、ピン留めは中央ペインに固定表示し、右ペインのタブシート（ピン留めタブは含まない、【アクティビティ】がデフォルト）は非stickyのまま変更しない。
* **対ユーザー操作メニュー（`ActionsMenu`）:** 自分以外のプロフィールでは、フォロー中/フォロー・ミュート/ミュート解除・ブロック/ブロック解除を1つのケバブメニュー（トリガーボタン＋ポップオーバー）に統合する。フォローは重要な操作のため、独立したフォロー/フォロー解除ボタンとしても引き続き併設し、メニュー内にも同じ操作を重複して持たせる。ブロックは破壊的操作（フォロー関係の強制解除を伴う、Bsky準拠の相互完全非表示。`docs/protocols.md` 10節）のため、実行前に確認モーダルを挟む。相手からブロックされている場合は「このユーザーからブロックされています」を表示し、フォロー操作を無効化する。フォロー/フォロー解除ボタンの左には、相手が閲覧者をフォロー中の場合のみ「フォローされています」という軽いテキストラベルを添える（`ProfileResponse.is_followed`、Misskey互換API`UserDetailed.isFollowed`に準拠）。

### 2.2b 投稿カード（`NoteCard`）のアクションメニュー
* 返信・引用・リポスト・リアクション・ケバブメニューの5つを下部に同じ体裁（アイコンのみ、キャプション文言なし）のボタン列として並べる。文言は `title` 属性（ツールチップ・アクセシブル名）にのみ残す。同じ操作をケバブメニュー（`ActionsMenu`）にも重複して持たせる（プロフィール操作メニューと同じ「重要操作は併設＋メニューにも複製」方針）。
* 各アイコンの隣に件数（返信数・引用数・リポスト数・リアクション合計数）を表示する。件数が0の場合は数値を表示しない。1000以上は`K`（小数点以下1桁まで）、100万以上は`M`表示にし、常に3桁以下に収める（`formatCount`、`docs/database.md` の `posts.reply_count`/`quote_count`/`repost_count` 参照）。
* リポスト済み・リアクション済みの状態は文言ではなくボタンを枠で囲う（`actionBtnActive`）ことで表現する。非公開投稿でリポスト不可の場合は薄く（`opacity`）表示し、クリック不可を示す。
* ピン留めは自分の投稿にのみ表示し、独立ボタンは持たずメニュー内のみに置く。
* 削除も自分の投稿にのみメニュー内（赤字・破壊的操作）に表示し、実行前に確認モーダル（`Modal`）を挟む。削除は連合先・Bluesky双方への取り消し配送を伴う不可逆操作のため（`docs/protocols.md` 4節）。

#### 添付画像のライトボックス表示（#64）
* 添付画像（動画/音声を除く静止画）をクリックすると、新規タブへの遷移ではなくページ内ライトボックス（`ImageLightbox`）をオーバーレイ表示する。オーバーレイクリック・表示中の画像自体のクリック・Escキーのいずれでも閉じる（#170）（`Modal`と同じ操作性だが、タイトルバー・枠のないボーダーレスな画像ビューア用の専用コンポーネント）。複数の静止画がある場合は左右矢印キー、左右スワイプ、画面上の前後ボタンで移動でき、先頭では前ボタン、末尾では次ボタンを表示しない（#153）。
* 画面幅600px以下（スマホ想定）では画像をオーバーレイの余白なしで画面横幅・縦幅いっぱいまで表示する。ページめくりボタンは`position: fixed`で独立配置のため、狭い画面では画像に重なることを許容する（#170）。
* 閲覧注意（NSFW）画像はカード上で初期状態をぼかし、右上の👁️だけで解除する。解除後の画像クリックは再びぼかす。ぼかした画像クリックで開くLightBoxもぼかした状態で、👁️からのみ解除できる。LightBoxを閉じると常に解除状態を破棄する。
* FediのCW付き投稿は警告文だけを初期表示し、ボタン操作で本文・添付メディア・URLカード（YouTube/Spotify等の埋め込みプレーヤーを含む）・アンケート・引用ブロックをまとめて開閉する（これらはNSFW画像の自動ぼかしとは別に、CWが閉じている間は`<NoteAttachments>`・`<LinkCard>`・アンケートUI・`<QuoteCard>`自体を描画しない）。リポスト先の元投稿（`Note.renote`）は別カードとして自身のCW状態を独立に持つため対象外。CW警告文中の`:shortcode:`も本文・表示名と同じ`Note.emojis`でカスタム絵文字画像へ展開し、通常カードと引用カードの両方へ適用する（#201）。WebSocketで新着投稿が出現した場合も通常APIの完全な投稿データで補完し、アンケート・添付・引用カードをリロードなしで表示する。
* ライトボックスの最大表示サイズはCSS上で1024×1024px（アスペクト比維持、`object-fit: contain`）。添付画像アップロード時の最大リサイズサイズ2048×2048px（`storage/image.rs`）がRetina（2倍密度）ディスプレイでの実質1024 CSS px相当の表示を見込んだサイズであることに合わせている。
* リモートサーバー由来の添付・アバター・カスタム絵文字はメディアプロキシ経由で表示する。同一オリジンのアップロード画像は直接表示する。管理画面「サイト設定」で外部Misskey互換メディアプロキシのベースURLを設定でき、空欄時は内蔵 `/proxy` を使う（#87）。
* 複数枚添付時も次/前送りナビゲーションは持たず、クリックした1枚のみを表示する。

#### GIFアニメの自動再生表示
* Tenor/Klipy GIFピッカー由来、またはBskyのGIFファイル直接アップロード由来（`presentation:"gif"`、`docs/protocols.md`参照）の動画添付は、`NoteAttachment.isGif`が`true`の場合`HlsVideo`を自動再生・ミュート・ループ・コントロール無し表示に切り替える（`autoplay muted loop playsinline`、`controls`は付けない）。それ以外の通常動画添付は従来通り`controls`付きで、クリック/再生ボタン操作するまではポスター（サムネイル）静止画のまま。
* HLS（`.m3u8`、GIFファイル直接アップロード由来を含むBsky動画全般）はsrcを`mediaUrl`によるメディアプロキシ経由にせず、動画CDN（`video.bsky.app`、`access-control-allow-origin: *`でCORS許可済み）を直接参照する。プロキシの許可Content-Type（`image/`/`video/`/`audio/`）に`application/vnd.apple.mpegurl`が一致せず502になる上、プロキシ経由だとHLSプレイリスト内のセグメント相対パスもブラウザ側で正しく解決できないため（`NoteAttachments.tsx`）。サムネイル（poster）は通常の画像なので引き続きプロキシ経由。
* HLSは`src`をJS側で遅延セット（hls.js `attachMedia`、またはSafariネイティブ再生時の`video.src`代入）するため、マウント時点の`autoPlay`属性だけでは再生が始まらない。GIF表示時はHLSソース確定後（hls.jsは`Hls.Events.MANIFEST_PARSED`、ネイティブ再生は`src`代入直後）に明示的に`video.play()`を呼んで開始する（`HlsVideo.tsx`）。
* HLS以外の通常動画添付（自インスタンス以外＝メディアプロキシ経由になるもの）は、`<video>`に`<source>`をプロキシ経由URL・直URLの順で2本並べる。プロキシが容量上限（25MiB）超過等で読み込みに失敗した場合、ブラウザが自動的に次の`<source>`（直URL）へフォールバックする。自インスタンス由来（`mediaUrl`が直URLのまま返る）の場合は元々プロキシを経由しないため`<source>`は1本のまま（`HlsVideo.tsx`のfallbackSrc、`NoteAttachments.tsx`）。

#### URLカード（`LinkCard`）
* Bsky受信投稿の`app.bsky.embed.external`（GIFピッカー由来を除く。GIFは添付動画として`NoteAttachments`側で表示）、およびFedi受信投稿の本文中リンク（`docs/protocols.md`「Fedi投稿のURLカード」参照）を、添付メディアの直下に表示する（`frontend/src/components/note/LinkCard.tsx`）。`Note.linkCards`は配列で、Bskyは常に0〜1件だがFediは本文中の複数リンクぶん**複数枚が縦に並ぶことがある**（各カードは`key={card.url}`で独立してmapされ、`indent`propで通常カード/QuoteCard内の左インデントを出し分ける点はBsky・Fedi共通）。表示は`card.embedSrc`の有無だけで振り分ける3種（個別サービスのURL解析はフロントでは行わない）。
  * **埋め込みプレーヤー**（`card.embedSrc`が存在する場合）: 初期状態はサムネイル+再生ボタンのみ。クリックした時点で`embedSrc`（バックエンド側のoEmbed discoveryで解決され、管理画面のホワイトリスト判定を通過したiframe src）を読み込む。既定でYouTube/Spotify/Apple Music/SoundCloud/Vimeoが対象（`site_settings.oembed_allowed_domains`、`docs/database.md`参照）。管理者がホワイトリストへドメインを追加するだけで対応サービスを増やせる。iframeには`sandbox`属性（トップレベルナビゲーション禁止等）を付与する。
  * **x.com**（x.com/twitter.com、`embedSrc`が無い場合のみ）: 初期状態はサムネイル+タイトル+説明のカード。クリックした時点で`platform.twitter.com/widgets.js`を読み込み、ツイート本文をライブ埋め込み表示する（widgets.jsは複数カードがあっても1回だけ読み込む）。
  * **上記以外の一般URL**: サムネイル+タイトル+説明+ドメイン名のカードをクリック可能なリンクとして表示するのみ（埋め込みなし、クリックで新規タブ遷移）。
  * いずれも埋め込みの実読み込みはユーザーのクリックまで発生させない（第三者トラッキング・iframe読み込みの既定回避、Mastodon等と同様の方針）。

#### 絵文字リアクションピッカー（`ReactionPicker`）
* トリガーボタンをクリックすると `Modal`（`EmojiPickerPanel`）が開く。検索欄＋タブ（よく使う／絵文字／カスタム）＋グリッドの構成。
* 検索欄に文字を入力すると、タブ表示を隠し、カスタム絵文字（shortcode/タグの部分一致）とUnicode絵文字（英語名の部分一致）を横断した検索結果を表示する。
* 「よく使う」タブは自分が現在付けているリアクションを頻度順に集計したもの（`GET /api/reactions/frequent`）。1投稿1リアクションの制約上、これは「過去の使用履歴」ではなく「現在も自分が付けているリアクションの集計」という近似値。
* Unicode絵文字データセットはビルド時に独立チャンクへ分割し、ピッカーを実際に開くまでロードしない（バンドルサイズ対策）。
* カスタム絵文字の画像は正方形の枠に押し込めず、実寸のwidth/height比（`GET /api/emojis`が`media_files`由来で返す）に応じてグリッドセルを1〜4カラム分（`emojiAspectSpan`、閾値2/3/4）まで広げて横長のまま表示する（`grid-column: span N`）。Unicode絵文字・カスタム紐付けのないリアクション画像（フォールバック表示）は常に1カラム。
* カスタム絵文字画像は`EmojiImage`コンポーネントが`media_files.blurhash`をクライアント側でcanvasにデコードしたプレースホルダを先に表示し、本画像の`onLoad`と同時にプレースホルダをDOMから除去して入れ替える（重ね描画ではなく除去のため、本画像の透過部分にプレースホルダ色が透けない）。

#### リアクションチップのホバーポップオーバー（`ReactionChips`）
* 各リアクションチップ（`NoteCard`下部・ポスト詳細画面の両方）にマウスオーバーすると、そのリアクションを付けたアクター一覧（アイコン＋名前、`GET /api/notes/:id/reactions/:content/actors`、新しい順・最大50件）をポップオーバー表示する。`ReplyIndicator`と同じ「初回ホバーのみフェッチ・120ms遅延クローズ」パターン。
* 未認証でも公開投稿なら閲覧できる（投稿の可視性チェックは `get_note` と同じ経路）。

### 2.3 【ポスト詳細（会話ツリー）画面】表示時
* **この画面（`/notes/:id`）はログイン不要で閲覧できる。** `App.tsx`のルーティングで`RequireAuth`によるガードを外しており、未ログイン状態でも閲覧できる（可視性の判定自体は各APIが`MaybeAuthedUser`で行うため、フォロワー限定等の非公開ポストは従来通り閲覧者に応じて弾かれる）。リアクション・リポスト・返信などの書き込み系操作は未ログインでも一見押下できるが、実行するとAPI側の401でエラートースト表示になる（他画面同様、明示的なログイン誘導は投票のみ）。
* **未ログイン時、左メニュー最下部のユーザーチップは`/login`への誘導ボタン（`LeftNav`）に差し替わる。** `composeBtn`（投稿ボタン）と同じ青背景の全幅ボタンで、遷移先は`/login?redirect=`に現在のパス・クエリ（`?tab=`含む）を載せた形にし、ログイン後に元のポスト詳細画面へ戻す。ログアウトボタン（⏻）は非表示になる。左メニューがアイコンのみに畳まれる幅（769〜900px）ではラベルの代わりに🔑アイコンを表示する（通常幅・モバイルドロワーではアイコンなしのテキストのみ）。
* **中央ペイン:** ターゲットポストを中心に、上に「リプライ元の垂直遡りツリー」を表示。直系リプライ・引用ポスト群は右ペインの「返信」タブ（モード2、下記）に統合されており、中央ペインには表示しない。
* **右ペイン (タブ切り替え式、タブシートは右ペイン上端にsticky固定される):**
  * **モード1: 【投稿者】** 投稿主のプロフィール概要（アイコン・表示名・アカウント名・自己紹介・フォロー中/フォロワー数）と固定ポスト一覧を表示する（`AuthorPanel`）。プロフィール概要部分はプロフィール画面へのリンクになっている。**リポストラッパーの場合、ここでいう「投稿主」はリポストした人（`note`自身）を指す**（リポストという行為自体をその人の投稿として扱う考え方、モード6参照）。
  * **モード2: 【返信】** ターゲットポストへの直系リプライ・引用を再帰的に辿るツリー表示（`ReplyThreadPanel`）。`GET /api/notes/:id/replies`（`reply_to_post_id`/`quote_of_post_id` を辿る`WITH RECURSIVE`、深さ20・最大200件で打ち切り）がフラットな配列を返し、フロント側で各ノートの`replyId`/`quoteId`から対象ポストを根とするツリーを組み立てて描画する。
  * **モード3: 【前後のポスト】** タブを開くと同時に（ボタン操作不要で）読み込みを開始し、ターゲットポスト（拡大文字表示NoteCard）を中心に前後の投稿を最大5件ずつ表示する。読み込み完了時、対象ポストの位置まで自動スクロールする。他人のリプライに邪魔されることなく、投稿主の「連投（ツリー投稿）」や「直前のリポスト」の文脈を単一画面で一気読みできる。表示順は上から: 「もっと新しい投稿を読み込む」ボタン → 新しい投稿（最大5件、ターゲットに近いものほど下） → **ターゲットポスト自身（拡大文字表示NoteCard）** → 古い投稿（最大5件、ターゲットに近いものほど上） → 「もっと古い投稿を読み込む」ボタン。読み込みボタンはそれぞれ`GET /api/notes/:id/context`に`before_id`/`after_id`（現在読み込み済みの最古/最新ポストID）を渡して続きを取得する（`before_limit`/`after_limit`を0にすると片方向のみ取得）。この機能は右ペインのタブとしてのみ提供し、中央ペインへの同内容の複製表示は行わない（狭幅では右ペインが中央ペインの下に落ちるがスクロールすれば到達できるため）。
  * **モード4: 【絵文字リアクション ＆ メンツ一覧】** ポストに付いたすべての絵文字（Fediのカスタム絵文字、ATPのLike等）を絵文字ごとにグループ化し、各グループの直下にそれを付けたアクター（アイコン・名前）の一覧を常時展開表示する（`ReactionListPanel`。ホバー不要で全件を一覧できる、`GET /api/notes/:id/reactions/:content/actors`を絵文字ごとに並列取得）。`NoteCard`下部のチップ表示（`ReactionChips`、ホバーでポップオーバー）とは別コンポーネント。
  * **モード5: 【リポスト】** 対象ポストをリポストしたユーザーと時刻の一覧（`RepostListPanel`、`GET /api/notes/:id/reposts`）。同一ユーザーが複数回リポストしていればその回数ぶんレコードが並ぶ。取り消し済み（Undo済み）のリポストも履歴として表示するが、詳細画面が存在しないためリンク化しない。取り消されていない行はクリックでそのリポストラッパー自身の詳細画面（`/notes/:id`）へ遷移する。
  * **モード6: 【元投稿者】（リポストラッパーの場合のみタブが増える）** リポスト元の実体（`note.renote`）のプロフィール概要と固定ポスト一覧を、モード1と同じ`AuthorPanel`で表示する。モード1がリポストした人向けなのに対し、こちらは本文の書き手を見るための導線。タブは既存の5モードの末尾に追加する（`noteDetailTab`はポストを跨いでセッション内保持されるインデックスのため、間に挿入すると通常ポストとリポストラッパーとでタブの意味がズレてしまう）。

### 2.4 右ペインにおけるサブタブ・ステートの維持ルール
* ユーザーが中央ペインで「ポストA」から「ポストB」へと詳細画面を切り替えた際、右ペインのコンテキスト自体はリセットされるが、**「現在アクティブなサブタブのインデックス（例: 『前後のポスト』モード）」はセッション内で維持（リテイン）**される。
* これにより、タイムライン上のポストを上から順番にクリックしていくだけで、画面を切り替えることなく、常に右ペインで「そのポストを投げた人の前後の文脈」を連続して覗き見ることができる超高効率なブラウジングUXを実現する。
* **ポスト詳細画面のタブ選択はURLの`?tab=`にも同期する（#226）。** タブ切り替えのたびに`history.replaceState`相当（`react-router`の`replace: true`）でURLへ反映するため、ブラウザの戻る操作の履歴段数には影響しない。ページをブラウザリロードした際は、URLの`?tab=`が存在すればそれを最優先で復元し（無ければセッション内で維持されている値をそのまま使う）、タブ選択がリロードをまたいで保持される。
* **ホーム画面右ペインのタブシート（【通知】/【トレンド・検索】）は`top={0}`でPC幅の右ペイン（`aside`自身が`overflow-y: auto`で独立スクロール）上端にsticky固定される。** 右ペイン内には直上に別のsticky要素（headerに相当するもの）が無いため、他画面（投稿詳細・管理画面）のようなheader実高さぶんのオフセットは不要で`top`は常に0。既に選択中のタブを再クリックした場合はタブ切替（無変化）ではなく右ペイン先頭へスクロールする。右ペイン全体を包む要素に対して`scrollIntoView({ behavior: "smooth", block: "start" })`を呼ぶことで、PC幅・スマホ幅（`aside`が`position: static`でwindowスクロールに合流）のどちらでも、ブラウザが適切な祖先スクロールコンテナを辿って先頭へ揃える（`HomePage.tsx`の`handleTimelineTabChange`）。
* **「前後のポスト」タブのスクロール位置もポストIDごとにセッション内（`RightPaneContext`、インメモリ）で記憶する（#226）。** 同タブを離れる（タブ切り替え・別ポストへの遷移・アンマウント）直前に右ペインのスクロール位置を保存し、ブラウザバックで同じポストの詳細画面に戻った際にそのスクロール位置を再現する。記憶が無い（初回訪問）場合は対象ポスト自身（拡大文字表示NoteCard）の位置まで自動スクロールする。

### 2.4b 中央ペイン（ホーム画面）のフィードタブ・スクロール位置の維持ルール
* 【タイムライン画面】中央ペインのフィードタブ（ホーム/ローカル/ソーシャル/グローバル/リスト/ハッシュタグ）選択状態・直近取得済みの一覧・スクロール位置は、`HomeFeedContext`（`<Routes>`の外側、2.4のRightPaneContextと同じ設計パターン）にセッション内で維持される。選択状態はLocalStorageにも保存し、リロード後に復元する（#90）。保存値が無い・破損している場合はホームを選択する。
* 他画面（投稿詳細・プロフィール等）へ遷移してから戻ってきても、直前に選んでいたタブと一覧・スクロール位置がリセットされず、再フェッチなしでそのまま復元される。フィードタブを行き来する場合も同様（タブごとに個別キャッシュ）。
* 既に選択中のフィードタブを再クリックした場合はタブ切替（無変化）ではなく、`window.scrollTo({ top: 0, behavior: "smooth" })`でタイムライン先頭へスクロールする（`HomePage.tsx`の`handleFeedTabClick`）。
* **キャッシュもスクロール位置の記憶も無い（このセッションで一度も表示していない）タブへ切り替えた場合は、前のタブのスクロール位置を持ち越さず即座に先頭（`window.scrollTo(0, 0)`、アニメ無し）へリセットする。** 持ち越すと新しい一覧が読み込まれる前後で見た目の高さが変わり、スマホ幅では右ペイン相当の領域（タブシート）まで巻き込んでスクロールしてしまうため。
* **狭幅（`useIsNarrowViewport`、1400px以下。右ペインが中央ペインの下に落ちる幅、`ProfilePage`/`ListsSettingsPage`と共通のフック）では右ペイン（通知/トレンド・検索のタブシート）自体を描画しない。** ホーム画面の中央ペインはタイムラインの無限スクロールでどこまでも続くため、この幅では右ペインへ確実にたどり着く手段が無い。にもかかわらず`NotificationsPanel`はマウント時点で通知を既読マークしてしまうため、一度も見ていない通知が既読扱いになる不具合があった。他画面（プロフィール等）のように中央ペインへ同内容を差し込んで表示する代替は行わず、単に非表示にする（既読マークの前提となる「実際に見た」を保証できないため）。

### 2.4b 投稿フォームの操作ボタン（#152）
* 投稿本文の直下の1行に、ポスト言語選択ボタン・Fediverse配送・Bluesky配送のON/OFFアイコンボタン（いずれもソース内へ同梱したロゴSVGを用いる正方形ボタン）・メディア添付ボタン（線画のみの自作SVGアイコン、Unicode絵文字に「図画」を的確に表す字が無いため）・残り文字数（行右寄せ）を横並びに配置する。公開範囲の選択はここでは行わない。
* **ポスト言語選択（Fediverse/Bluesky配送ボタンの左隣）**: 他のアイコンボタンと同じ正方形で、現在選択中の言語を`JA`のような2文字コード（大文字）で表示する。クリックするとポップアップリストが開き、`JA 日本語`のように2文字コード＋ネイティブ表記併記の選択肢（表示言語設定と同じ7言語、`docs/protocols.md` 3節「ポストの言語」参照）から選べる。初期値は現在の表示言語で、Fedi/Bsky配送先トグルのように「最後に送信した値」を記憶する方式ではなく、投稿のたびに現在の表示言語へ戻る。このプロパティはBsky配送（`app.bsky.feed.post`の`langs`）にのみ反映され、Fedi配送には影響しない。Bsky実体を持たない返信先（`bskyReplyAllowed`が偽）ではBluesky配送ボタンごと非表示になる。
* フォーム最下段には投稿ボタンを3種並べる：🌐投稿（パブリック）・🌙ひかえめ・🔒️プライベート。それぞれ押した時点の公開範囲でただちに投稿されるため、公開範囲は「事前にトグルで決めてから送信する」のではなく「送信ボタンそのものが公開範囲を兼ねる」形になる。両立できない組み合わせを選んでからエラーで弾く体験を避けるため。
* Bluesky配送がONの間は🔒️プライベートボタンをグレーアウト（disabled）する（BskyはプロトコルAPI上followers_only投稿を配信できないため）。ホバーまたはクリックで、Blueskyロゴ付きの吹き出し（「Blueskyをオフにするとプライベート投稿ができます」）をボタン下に表示する。disabled化されたネイティブbutton要素はポインタイベントを拾わないため、ホバー/クリック判定は親wrapper要素側で行い、button自体は`pointer-events: none`で透過させる。
* 引用対象が「ひかえめ」投稿の場合、🌐投稿（パブリック）ボタンをグレーアウトする（ひかえめ投稿の引用はひかえめ・プライベートでのみ可能なため）。
* 返信時のFediverse/Bluesky配送ボタンは、返信先ポストが実際に持つプロトコルのみ表示する（`Note.replyFediAllowed`/`replyBskyAllowed`。持たないプロトコルへ配送すると返信先と無関係な独立投稿として誤配信されるため、選択肢自体を出さない）。返信時の投稿ボタンも通常投稿と同じ3種並びだが、返信先の公開範囲より広い範囲は選択肢に出さない（公開範囲は狭めることはできても広げることはできない設計）。返信先がひかえめならひかえめ・プライベートの2つ、プライベートならプライベートのみ（この場合これ以上狭められない旨のテキストも併記）。Bluesky配送がON（またはBluesky実体しか持たない返信先）の間は🔒️プライベートボタン自体を非表示にする（グレーアウトではない。返信では選択肢が返信先から動的に絞られるため、常時押せないボタンを出すより無い方が分かりやすいという判断）。
* **デフォルトの投稿ボタン（Ctrl+Enter等のショートカット送信先）を5px幅の赤枠（`box-shadow`、ブラウザ既定のフォーカスアウトラインは`:focus-visible`で無効化して代替）で明示する**：Tabキーでいずれかの投稿ボタンにフォーカスが乗っている間はそのボタンが赤枠マーカーの対象になり、フォーカスが外れると通常投稿・引用は「最後に送信した投稿ボタンの公開範囲」（`localStorage`キー`seiran:composer-defaults`、配送先トグルの状態も一緒に記憶し次回の初期値にする）、返信は返信先の公開範囲から決まるデフォルト値（`replyVisibilityConstraint`）へ戻る。赤枠は対象ボタンが公開範囲の相互排他でグレーアウト中でも消さない（例: プライベートがデフォルトのままBluesky配送をONにした場合）。この状態で本文エリアからCtrl+Enter等のショートカットを使うと、意図しない公開範囲へ無言で送信してしまわないよう、送信の代わりにパブリック投稿ボタンへフォーカスを移す。
* **投稿ボタン列・操作ボタン列内の矢印キーナビゲーション**：いずれかの投稿ボタン（🌐/🌙/🔒️、返信は絞り込まれた1〜3個）にフォーカスがある間、左右矢印キーでそのボタン群内をフォーカス移動する（グレーアウト中のボタンは読み飛ばし、端まで行くと反対側へ折り返す）。上矢印キーでBluesky配送ボタンへ移動する。Fediverse配送・Bluesky配送・添付・アンケート・CWの操作ボタン（レンダリングされているもののみ、最大5個）にフォーカスがある間も同様に左右矢印キーで行き来でき、上矢印キーで本文入力欄（`ComposerEditor`が`forwardRef`で公開するcontentEditable要素）へ、下矢印キーでデフォルトの投稿ボタン（グレーアウト中ならパブリック投稿ボタンへ代替、それも不可なら無反応）へ移動する。
* 狭幅画面で投稿ボタン列が折り返しても画面幅を押し広げないよう、投稿フォーム内の各行コンテナ（`.form`/`.controlRow`/`.bottomRow`/`.footer`/`.postBtnGroup`）はNoteCardと同じ`min-width: 0`の徹底により、子要素の内容幅がページ全体の横幅を強制的に広げないようにしている（横方向のはみ出しはモバイルでフローティングボタン群の位置がずれる不具合の原因になるため、`body`の`overflow-x: hidden`と合わせた二重の対策）。
* **複数添付（#227）**: メディア添付ボタンは`<input type="file" multiple>`で、1回の選択または複数回の追加操作で最大10件（バックエンドの上限と同じ）まで添付できる。添付プレビューはフォーム最下段に横並びグリッド表示され、各アイテムに個別の削除ボタンを持つ（1個の削除が他の添付に影響しない）。
* **Bsky embed選択のラジオボタンリスト（#227）**: Bluesky配送がONの間、添付ファイル（非アニメ静止画グループ・アニメGIF・動画/音声それぞれ）と本文中のURL（生URL、最大5件）を合わせた「Bsky embed候補」から、次のいずれかを満たす場合にラジオボタンリストを表示する（`.attachGrid`とは別の行に配置、`.bottomRow`は縦積みflexで両エリアを分離）。
  * 候補が2件以上ある（複数種類が同時に使われている、曖昧さがある）
  * 本文中にURLが1件でもある、またはURLが既に選択済み（添付ゼロ・本文URLゼロの状態からURLリンクカードを添付する唯一の手段が「本文へ一旦URLを書く→ラジオリストで選ぶ→本文から消す」という孤児化フローのため、候補が1件〔そのURLのみ〕でもリストを出す。Blueskyの「URL貼り付け→プレビューカード→本文中の文字列を消してもカードは残る」操作にほぼ相当）
  * 候補がURL以外の1件だけ（例: 静止画のみ）の場合は表示しない（曖昧さが無いため）。
  * 候補はアニメGIF・動画/音声それぞれに小さな正方形サムネイル（`DriveFile.thumbnailUrl`、無ければ画像は元URL・動画/音声はサムネイル無しでラベルのみ）を添える（「動画1」等の表記だけでは判別できないため）。
  * **送信ブロックは「候補が2件以上あるのに未選択」の場合のみ**（投稿ボタン群を`disabled`）。候補がURL単独1件だけの場合は選ばなくても送信できる（未選択ならバックエンドの固定優先順位でそのURLがそのまま採用される、`docs/protocols.md`3節「Bsky embed選択」参照）。
  * 本文中のURLを選択した状態でそのURLを本文から削除しても、ラジオボタン項目・選択自体は消えない（孤児として残る）。他の項目を選び直せばその孤児項目は自然にリストから消える。
  * Bluesky配送をOFFにすると、ラジオボタンリスト自体が非表示になり選択もクリアされる。
  * バックエンド側には選択必須のハードエラーは無い（省略時は固定優先順位で自動選択）。
* **URLリンクカード添付のチェックボックスリスト**: ラジオボタンリストが表示されない状態
  （Bluesky配送がOFF、またはCW有効中）でも本文中にURLがあれば、代わりにチェックボックス
  リスト（複数選択可）を表示する。seiranは（Bskyと違い）1投稿に複数のURLリンクカードを
  同時に持てるため、ラジオボタンではなくチェックボックスにしている。候補はラジオボタン
  版と同じ「本文中のURL（生URL、最大5件）＋チェック済みだが本文から消えた孤児URL」。
  * チェックしたURLを本文から削除してもチェック項目自体は消えない（孤児として残る、
    ラジオボタン版のURL孤児化と同じ仕様）。
  * チェックボックスリストが表示される状態からラジオボタンリストが表示される状態
    （Bluesky配送ONかつCWオフ）へ切り替わった瞬間、チェック済みURLのうち最もインデックス
    の小さいもの（表示順で最も上のもの）がラジオボタンリストの選択へ引き継がれる
    （既に明示選択がある場合は上書きしない）。
  * 送信のブロックは行わない（0件チェックでも送信できる）。
* **アンケート作成（#228）**: メディア添付ボタンの隣に📊トグルボタンがあり、開くと選択肢テキスト
  入力（初期2件、+ボタンで最大10件まで追加・×ボタンで最小2件まで削除）・複数選択チェックボック
  ス・期限選択（無期限/日時指定`<input type="datetime-local">`/経過時間プリセット5分〜7日の
  ボタン列）を表示する（`.attachGrid`・Bsky embed選択リストと同様、`.bottomRow`内の独立した行）。
  メディア添付との併用は禁止しない。
  * 非空選択肢が2件揃うまで送信ボタン群を`disabled`にする。
  * 有効なアンケートは常にBsky embed候補の先頭・最優先項目として並ぶ（`docs/protocols.md`
    3節「アンケート」参照）。トグルボタンを閉じる（アンケートを削除する）と選択肢・期限設定は
    すべてリセットされる。
* **CW（閲覧注意）作成（#229）**: アンケートトグルの隣に⚠️トグルボタンがあり、開くとCWガイド文
  の1行テキスト入力欄（100書記素まで、残り文字数表示）を表示する（`.bottomRow`内の独立した行、
  アンケート編集ブロックより上）。メディア添付・アンケート作成との併用は禁止しない
  （Fedi側には通常通り配送されるため）。
  * ガイド文が空（trim後）、または100書記素を超える間は送信ボタン群を`disabled`にする。
  * **CWが有効な間はBsky embed選択のラジオボタンリスト自体を表示しない**（候補計算も行わない）。
    隠された本文・添付物・アンケート・引用すべてを見るには常にURLリンクカードから
    seiranの記事詳細ページへ飛ぶ設計のため、選ぶ余地が無い（`docs/protocols.md`3節「CW」参照）。
  * トグルボタンを閉じる（CWを削除する）とガイド文はリセットされる。

### 2.4c 中央ペイン上部の常設投稿フォームの折りたたみ
* 【タイムライン画面】の中央ペイン最上部に常設される投稿フォームは、トグルボタンで開閉できる。折りたたみ状態は`localStorage`（キー: `seiran_composer_collapsed`）に永続化され、次回訪問時も維持される。
* 新規投稿ダイアログを未投稿のまま閉じた場合、保存した書きかけ（本文・添付・配送先・公開範囲）を、既に表示中のホーム上部投稿フォームへ即時反映する。

### 2.4d フィードタブのスクロール追従
* 【タイムライン画面】のフィードタブ（ホーム/ローカル/ソーシャル/グローバル/リスト/ハッシュタグ切り替え）は、下スクロール時に画面上部の見出し（`panel.header`、両方とも`position: sticky`）の直下に張り付いたまま残る。見出しの実高さを`ResizeObserver`で計測し、フィードタブの`top`オフセットに反映することで、2つのsticky要素が重ならないようにしている。

### 2.4e タイムラインへのリアルタイム新規ポスト挿入時のスクロール位置維持
* WS経由で届いた新規ポスト（自分の投稿を含む）は一覧の先頭へ挿入される。スクロール位置が最上部（`window.scrollY === 0`）の場合は、従来通りpush-downアニメーション（`.entering`、高さを0.4秒かけて0から展開する演出）付きで挿入される。
* スクロール位置が最上部でない場合は、見えているポストが挿入によって動かないようにする。アニメーションなしで即座に確定高さで挿入し、挿入前後で増えた高さぶんだけスクロール位置を同時に補正する（挿入前の`scrollHeight`との差分を`scrollY`へ足し込む）ことで、見た目の位置を相殺する。

### 2.4f 復帰時・WebSocket再接続時のタイムライン再同期
* 【タイムライン画面】は次の2つのタイミングで、表示中一覧の先頭を補完する再同期処理（先頭ページ相当＝`PAGE_SIZE`件の再取得＋マージ）を行う。どちらも同じマージ処理（`mergeHeadIntoTimeline`）を共有する。
  * 他画面（投稿詳細・通知等）から戻ってきた時（ブラウザバック・アプリ内リンク遷移のどちらでも、`HomeFeedContext`のキャッシュを復元した直後）。離脱中はチャンネル購読・リアクション購読ともに切れているため、その間の新着・リアクション変化・削除が反映されないままキャッシュが古くなっている。
  * WebSocketが不意に切断して再接続した時（`StreamingContext`の`subscribeChannel`に渡す`onResync`コールバック）。切断中は同様に新着を取りこぼす。
* 再取得した先頭ページと現在の一覧をノートIDで突き合わせ、重なりが見つかった位置より新しい分だけを先頭へ追加する（アニメーションなし。スクロール位置維持は2.4eと同じ仕組みを使う）。
* 再取得した先頭ページと現在の一覧が**まったく重ならなかった場合**（`PAGE_SIZE`件を超える取りこぼしがあったとみなせる）は、取得できた分を先頭へ追加しつつ、境目に「取りこぼしの可能性」を示す区切り線（二重の波線、SVGマスクで描画）を挿入する。この区切りの位置（直後のノートID）は`gapBeforeIds`として`HomeFeedContext`のキャッシュにも保存され、画面を離れても表示が保持される。区切り線の上マージンは、直下のNoteCard間の余白（`.card`の`margin-top: 12px`＋区切り線自身の`margin-bottom: 2px` = 14px）に揃え、上下対称にしている。

### 2.4g タイムライン画面のスワイプ操作（モバイル）
* スマホでタイムライン画面を表示している際、コンテンツ領域を左右にスワイプすることでフィードタブを順番に切り替えられる。
* **左スワイプ** → 次のタブへ（ホーム→ローカル→ソーシャル→グローバル→リスト→ハッシュタグの順）
* **右スワイプ** → 前のタブへ
* タブ順序は表示順と一致（ホーム・ローカル・リスト群・ハッシュタグ群）。先頭・末尾ではそれ以上切り替わらない。
* 縦スクロールとの誤検知を防ぐため、横移動が縦移動の1.5倍以上かつ50px以上の場合のみスワイプと判定する（`useSwipe` フック、`touch-action: pan-y`）。
* タブ切り替え後、アクティブなタブ要素がタブバー内で見えるよう自動スクロール（`scrollIntoView`）する。

### 2.5 【メッセージ（DM）画面】表示時
* **右ペイン:** メッセージセッション（スレッド起点を同じくするdirect投稿の集合）の一覧。相手のアイコン・名前・最終メッセージのプレビュー・未読ドットを表示。「新規メッセージ」ボタンで宛先未選択の作成画面に遷移できる。参加者（自分以外）が全員ミュートまたはブロック対象のセッションは一覧・左ペイン未読バッジのいずれにも現れない（`docs/protocols.md` 9節）。
* **中央ペイン:** 選択中セッションのメッセージ履歴を**時刻順**（ツリー表示はしない）で表示し、**一番下が最新**のメッセージ。その下に送信フォーム（宛先chip入力欄 + テキスト欄）を固定表示する。
  * 既存セッションを開いた場合、宛先chipはそのセッションの相手で自動的に埋まる（返信のたびに宛先を選び直す必要はない）。
  * 宛先にBskyアクターが含まれる場合: 文字数上限がBsky DM準拠（1000書記素）に切り替わり、メディア添付ボタンが非表示になる。含まれなければ通常投稿と同じ上限・添付ボタンあり。
  * 宛先chip入力欄でBskyアクターと他プロトコルのアクターを混在させようとすると、警告の吹き出しが出て競合するchipが赤字表示になる（Bsky DMは1対1のみのため）。
* **左ペインバッジ:** 「メッセージ」項目に未読のあるセッション数を表示する。

### 2.6 【通知画面】（`/notifications`）表示時
* リポスト通知（🔁）と引用通知（❝）も既存の返信・リアクション通知と同じ一覧に表示し、通知文から新しく作られたリポスト／引用投稿へ遷移できる（#198）。
* **中央ペイン:** タイムライン画面右ペインの【クイック通知】タブ（`NotificationsPanel`）と同一コンポーネントをそのまま表示。新着順の無限スクロール、WS経由の新着シグナルによる差分取得に対応（`docs/protocols.md` 8節）。
* **右ペイン:** 【トレンド＆検索】固定表示（タブ切り替えなし）。

### 2.7 【設定画面】（`/settings` 以下）表示時（#55）
左ペインのメインメニューから「設定」で遷移する。右ペインは使わず中央ペインのみ。
* **`/settings`（設定メニュー）:** アカウント・プロフィール・ミュート/ブロック・プライバシー・リスト・表示・アプリトークンへの導線行の一覧。

## 3. ブリッジユーザーのインターセプション（案内）導線

プロトコルの歪みによって生まれた「影武者アクター」をユーザーが閲覧・操作した際、フロントエンドが能動的に介入するUX仕様。

### 3.1 本尊へのワープ機能
* バックエンドから返ってきたアクターオブジェクトの `bridge_real_actor_id` が埋まっている（＝自分が影武者である）場合、プロフィール画面の最も目立つ位置に「**本尊（オリジナルアカウント）はこちら**」というプロトコルアイコン付きのワープボタンを強制的にレンダリングする。

### 3.2 フォロー時のインターセプト
* ユーザーが影武者アクターの「フォロー」ボタンを押した瞬間、フロントエンドは即座に配送を処理せず、以下の確認モーダル（ダイアログ）を割り込ませる。

> **「このアカウントは、Bluesky（またはFedi）のユーザーがブリッジ経由で投影されている影武者です。 seiranの機能をフルに活用するため、本尊（オリジナルアカウント）を直接フォローすることをおすすめします。本尊をフォローしに行きますか？」**
> * [ボタンA]: 本尊のプロフィールへ移動してフォロー
> * [ボタンB]: そのまま影武者をフォロー（互換維持用）

### 3.3 リモートポスト・ユーザーの明示（「リモートで表示」バナー）
* ポスト詳細画面・ユーザープロフィール画面は、表示対象がローカルアクターでない場合、`panel.header` 直下（画面最上部）に共通コンポーネント `RemoteBanner` を表示する。「リモートのポストです」/「リモートのユーザーです」という文言 ＋ 別タブで開く「リモートで表示」リンクの1行バナー。
* リンク先URLは Fedi 由来（AP URI）を優先し、無ければ Bsky 由来（AT URI → `https://bsky.app/profile/{did}[/post/{rkey}]`）を使う。ポストは `NoteResponse.remoteUrl`（バックエンドが `posts.ap_object_id`/`posts.at_uri` から算出）、プロフィールは `ProfileResponse.ap_uri`/`at_did` から算出する。Fedi由来のURLは末尾が`/activity`の場合これを取り除く（Misskey・Mastodon等はActivity（Announce/Create）の`id`を`{閲覧可能URL}/activity`の形で発行し、末尾なしが実際にブラウザで開けるURLになるため。実測: `https://misskey.io/notes/{id}/activity`はAnnounce、`https://misskey.io/notes/{id}`はNoteかつHTMLも200を返す）。
* **リポスト詳細（`NoteDetailPage`）はリポストラッパー自身（`note`、リポストした人）でリモート判定・リンク先を決める。** リポストという行為自体はリポストした人の自己表現であるという考え方に基づく（元投稿`note.renote`がリモートかどうかは無関係）。ブリッジ（影武者）アカウントの本尊ワープ導線（3.1/3.2）とは独立した仕組みで、両方が同時に表示されうる。

### 2.2f 引用ポストカード

引用ポストは自身の本文を通常どおり表示し、その直下に引用元を枠付きカードで1段だけ表示する。引用カードには返信マーカー、ユーザー名、本文（CWは案内文・開閉ボタン付き）、時刻、添付メディア、アンケート、リアクションを表示する。引用元がさらに引用を持つ場合は「引用あり」とだけ表示し、その先のカードは入れ子にしない。引用元が閲覧者から見えない場合はAPIが `quote` を埋め込まず、従来の引用元リンクだけを表示する。

各投稿カードのアクション列とメニューには「引用」を表示する。選択すると引用元の投稿者・本文を確認できるコンポーザを開き、通常投稿と同じ本文・添付・可視性・Fedi/Bsky配送先を指定してコメント付き引用を作成する。

### 2.2g 未取り込み参照の表示（`PendingReferenceIndicator`、#234）

リプライ・引用・リポストの参照先が`pending`（未取り込み）/`gone`（消失確定）な場合、`Note.replyStatus`/`quoteStatus`/`renoteStatus`（対応する`*Id`が無い時だけ意味を持つ）に応じて以下を表示する。

* **リプライ**: 通常カード最上部の関係行（返信・引用リンクを並べる箇所）に、`ReplyIndicator`の代わりに`pending`なら「未取り込み」案内＋取り込むボタン、`gone`なら案内のみを表示する。
* **引用**: 引用カード（2.2f節）の位置に、`pending`なら「未取り込み」案内＋取り込むボタン、`gone`なら案内のみを表示する（引用元が閲覧者から見えないケース＝APIが`quote`を返さないだけで`quoteId`はある場合とは別の状態）。
* **リポストラッパー**: rail（🔁 + リポストした人 + 日時）は通常通り表示し、その下の元投稿カードの位置に、`pending`なら「未取り込み」案内＋取り込むボタン、`gone`なら案内のみを表示する（対象が見当たらないが誰かが何かをリポストしたこと自体は分かるようにする）。

取り込むボタンは`POST /api/notes/:id/resolve-reference`（body: `{"kind": "reply"|"quote"|"repost"}`）を呼ぶ。`resolved`が返れば、リプライは解決先IDでその場`ReplyIndicator`へ切り替え、引用・リポストは解決先を`GET /api/notes/:id`で取得して埋め込みカードへ切り替える（ページ全体の再読み込みは不要）。`pending`/`gone`が返れば表示をその状態へ更新する（再試行可能）。投稿詳細画面（`GET /api/notes/:id`）を開いた時点でも`pending`な参照はサーバー側が自動で解決を試みる（`docs/protocols.md` 1節「pending参照の遅延解決」）ため、ボタンを押す前に解決済みの表示へ変わっていることも多い。

# Unicode絵文字の表示（twemoji）

Unicode絵文字（本文中・表示名中・絵文字リアクション・絵文字ピッカーのグリッド・アクションメニューやナビの装飾アイコン等）は、OS/ブラウザのネイティブグリフに任せず、jdecked/twemoji（`@twemoji/parser` + `@twemoji/svg`）のSVGをセルフホストして統一表示する。アセットは `frontend/scripts/copy-twemoji-assets.mjs` が `npm install` の `postinstall` で `node_modules/@twemoji/svg` から `frontend/public/twemoji/` へコピーする（git管理外、`.gitignore`）。

- `lib/twemoji.tsx`: `@twemoji/parser` を `buildUrl: (codepoints) => "/twemoji/${codepoints}.svg"` でラップし、テキスト中のUnicode絵文字を検出してセルフホストURLを返す。
- `components/common/TwemojiImg`: 実際の`<img>`描画を担う共通部品。読み込み失敗時（`onError`）はOSネイティブの絵文字グリフへフォールバックする。`@twemoji/parser`（npm最新17系）と`@twemoji/svg`（npm最新15.0.0で更新停止）のUnicodeカバレッジにズレがあり、parserが検出した絵文字でもsvg側にアセットが無く404になることがあるため（新しめの結合絵文字・ZWJシーケンス等）、パッケージのバージョンを揃えるのではなくこのフォールバックで恒久対応している。
- `components/common/TwemojiEmoji`: 単一の絵文字文字列を`TwemojiImg`へ変換する（絵文字と判定できなければ元の文字列のままフォールバック）。ナビアイコン・バッジ・通知アイコン等で使う。
- `components/common/TwemojiText`: 絵文字混在テキスト（`"💬 返信"` のようなラベル）のUnicode絵文字部分だけを変換する。`ActionsMenu` の項目ラベルはここを通す。
- `components/note/EmojiText`: カスタム絵文字（`:shortcode:`）を`emojis`マップで画像化した残りのプレーンテキスト部分にも、上記と同じUnicode絵文字変換をかける（本文・表示名共通）。

絵文字部分がDOMの`textContent`に含まれなくなる（`<img alt="...">` になる。ただしtwemojiアセット読み込み失敗時はテキストへ戻る）ため、テストや実装でテキスト内容から絵文字混在ラベルを判定する場合は `textContent` ではなく `getByRole` のaccessible name（role + name）ベースで判定すること。
